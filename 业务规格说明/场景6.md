# 实操考核题册## 统一考核说明### 一、统一交付内容1. 完整项目：包含完成指定场景所需的前端、后端及相关服务实现，以及git地址。2. README：说明项目如何启动、环境与配置、数据初始化、模型配置、主要业务流程、已实现范围、重要技术取舍、简化或未完成内容，以及继续开发时的优先补齐方向。3. 接口文档：说明主要前后端接口及业务服务之间的契约，文档形式不限。4. 系统设计图：至少包含一张系统整体架构图，以及一张能够说明核心业务状态或关键交互时序的设计图。5. 现场 Demo：应试者需要现场演示完整业务闭环，并能够解释关键设计、数据一致性、权限与 AI/确定性规则边界。# 场景 6  软件交付 AI 助手的反馈、Trace 与知识库问答## 业务背景某软件公司为研发团队提供 AI 助手，用于生成发布说明、提供故障排查建议以及总结代码变更风险。上线后，研发用户可能反馈“答案不对”“引用了过期流程”“敏感 token 被写进 Trace”等问题。平台团队希望每一次 AI 回答都能够被追踪：知道使用了什么模型、什么提示词版本、什么检索证据、发生了哪类错误，并能够把用户反馈与具体 Trace 关联起来进行定位和闭环处理。同时，知识库问答需要基于发布规范、应急 Runbook 和开发规约等真实文档提供带引用的答案。## 业务角色1. 研发用户：使用 AI 助手、查看回答来源、提交质量反馈并查看自己的反馈状态。2. AI 平台运营：查看完整 Trace、领取和处理反馈、维护知识库内容。3. 安全管理角色：维护或验证敏感信息处理规则，保证 Trace 与日志不泄露不必要的敏感内容。## 业务目标|目标闭环<br />用户发起 AI 请求 → 后端创建可追踪的 trace 标识 → 检索知识、调用真实模型并处理输出 → 返回结果与引用 → 用户提交反馈 → 运营人员通过 Trace 定位模型、提示词、检索或结构化处理问题 → 调整后重新验证并关闭反馈。||---|## AI Trace每一次 AI 请求需要形成统一 Trace，并能够记录足以复盘的关键信息，例如业务场景、用户、业务对象、模型、提示词版本、检索摘要、耗时、状态、错误类型以及时间信息。Trace 标识应贯穿前端请求、后端编排、知识检索、模型调用和最终响应。普通研发用户只能访问与自己业务相关的 Trace 摘要和反馈；运营角色才能查看更完整的诊断信息。提示词版本必须是实际可查询字段，而不是只存在于代码注释中。历史 Trace 即使缺少新版本字段，查询页面也应能够安全展示而不是因为单条坏记录导致整体不可用。## RAG 知识库问答系统需要基于应试者自行准备的真实 Markdown、PDF 或其他文档建立最小可运行知识库。问答过程需要完成文档导入、内容切分、检索、真实模型生成以及来源引用。回答中的引用至少需要让用户知道来源文档和对应片段。检索证据不足时，应明确回答未找到充分依据，而不是由模型自行编造流程或规则。## 反馈闭环研发用户能够针对某次 AI 回答提交质量反馈。运营人员应能够筛选反馈、领取处理、记录处理结论，并将反馈推进到关闭或驳回等合理状态。重复关闭同一反馈不能产生重复业务动作。反馈处理过程需要保留操作者和时间，并能够从反馈反查对应 Trace，从 Trace 继续定位模型、提示词、检索证据和错误环节。## 敏感信息与错误分类Trace 和日志可能包含 API Key、访问令牌、手机号、邮箱等敏感信息。系统需要在持久化或展示前进行脱敏或最小化，不能把用户输入中的敏感值原样长期保存在可查看 Trace 中。错误不能统一表现为一个笼统的系统异常。系统需要能够区分模型不可用、知识检索无命中、模型输出无法解析、权限不足和内部异常等不同类型，使用户和运营人员知道问题发生在哪一层。## 需要正确处理的异常与边界1. 真实模型调用超时时，Trace 需要记录正确状态和错误类型，用户应得到可理解反馈。2. 知识检索没有返回有效证据时，系统应明确无充分依据，不得编造答案。3. 模型返回无法解析的结构化内容时，系统应记录结构化处理失败，并提供安全的失败结果。4. 用户输入中包含 API token 等敏感字段时，Trace 与日志展示应完成脱敏。5. 历史 Trace 缺少新版本字段时，查询和列表应能够兼容，不得因单条记录导致整体失败。## 完成后的业务结果最终应能够演示一次真实 AI 请求从知识检索、模型生成、引用展示到 Trace 查询，再由用户提交反馈、运营人员定位问题、调整知识或提示词后重新验证并关闭反馈的完整流程。
